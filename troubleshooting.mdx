Find your error message below. Tributary errors start with `error:` and usually name the table, column, or constraint involved.

<Tip>
  Run `plan` before `sync`. Most problems with the subset, such as missing tables, cycles, or bad schema files, show up in `plan` without writing anything.
</Tip>

## Setup and configuration

<AccordionGroup>
  <Accordion title='no connection named "..."'>
    ```text
    error: no connection named "prd" (known: prod, local); add it with: tributary config set connections.prd.url <postgres-url>
    ```

    The `--source` or `--target` name isn't in your config. Check the spelling against the `known:` list, or add the connection:

    ```bash
    tributary config set connections.prd.url 'postgres://...'
    ```
  </Accordion>

  <Accordion title="unknown config key">
    ```text
    error: unknown config key "conections.prod.url"; valid keys: ...
    ```

    Only `connections.<name>.url`, `allowlist`, `ai.provider`, `ai.model`, `ai.apiKey`, and `ai.baseUrl` can be set. See [Configuration](/configuration#settings).
  </Accordion>

  <Accordion title="Settings seem to disappear">
    Tributary may be reading a different config file. Run `tributary config path` to see which one. The `TRIBUTARY_CONFIG_DIR` and `XDG_CONFIG_HOME` environment variables change the location. See [Where settings are stored](/configuration#where-settings-are-stored).
  </Accordion>

  <Accordion title="Connection refused, timeout, or authentication failed">
    These come from Postgres, not Tributary. Check the URL with `psql`:

    ```bash
    psql "$(tributary config get connections.prod.url)" -c 'select 1'
    ```

    For managed databases, you often need `?sslmode=require` at the end of the URL.
  </Accordion>
</AccordionGroup>

## Seeds

<AccordionGroup>
  <Accordion title="every --seed-table needs a --where">
    ```text
    error: every --seed-table needs a --where (got 2 --seed-table, 1 --where)
    ```

    Seeds are pairs. Each `-t` matches the `-w` in the same position. To select every row of a table, use `-w true`.
  </Accordion>

  <Accordion title="no seed: pass --seed-table <table> --where <sql>">
    `plan` and `sync` need at least one seed. Add `-t <table> -w <sql>`.
  </Accordion>

  <Accordion title='no such table "..." in source schema'>
    The seed table doesn't exist. Bare names resolve to the schema file's `defaultSchema`, which is `public` by default. Use `schema.table` for other schemas, such as `-t billing.invoices`. Run `tributary inspect --source prod` to list tables.
  </Accordion>

  <Accordion title='table "..." has no primary key'>
    ```text
    error: table "public.events" has no primary key; tributary needs one to identify rows
    ```

    Tributary identifies rows by primary key, so every table in the subset needs one. Either add a primary key in the source, or stop the walk from reaching the table. Use `ignore` for a real foreign key, or remove the declared reference that leads there.
  </Accordion>

  <Accordion title="A SQL syntax error in the seed">
    The `-w` value is pasted into `WHERE (...)` as-is. Quote it for your shell so the SQL arrives intact. String literals use single quotes inside:

    ```bash
    -w "email = 'admin@example.com'"
    ```

    Multiple statements, such as `id = 1; DELETE ...`, are always rejected.
  </Accordion>

  <Accordion title="The plan is much bigger than expected">
    - Check whether you used `--traversal full`. The default `downstream` is much smaller.
    - Look at the **via** column to find the edge that pulls in the extra rows.
    - If a real foreign key pulls in unrelated data, such as `created_by` or `actor_id`, add it to `ignore` in the [schema file](/schema-configuration#ignore).
  </Accordion>

  <Accordion title="Expected rows are missing from the plan">
    - The relationship probably isn't a real foreign key. Declare it with `references` or `polymorphic` in the schema file. `tributary schema init` lists every `*_id` column that has no foreign key, so you can fill in its target.
    - Under `downstream` traversal, required parents don't fan out to their other children. See [Traversal modes](/how-it-works#traversal-modes).
    - Check the output for `no schema file: following database foreign keys only`. If you see it, Tributary didn't find your schema file. Run from the directory that contains it, or pass `--schema`.
  </Accordion>
</AccordionGroup>

## Schema files

<AccordionGroup>
  <Accordion title="invalid schema file">
    ```text
    error: ./schema.yaml: invalid schema file:
      - tables.orders.references.customer_ref: invalid target "users": expected "table.column" or "schema.table.column"
    ```

    Every problem is listed with its path in the file. Fix each one, then run `tributary schema validate --source prod`. See [File format](/schema-configuration#file-format).
  </Accordion>

  <Accordion title="not a tributary schema file: it needs `version: 1` at the top">
    Add `version: 1` as the first key.
  </Accordion>

  <Accordion title='no such column "..." on "..."'>
    A table or column named in the schema file doesn't exist in the source database. Check for typos, and use `schema.table` names for tables outside `defaultSchema`.
  </Accordion>

  <Accordion title='no catalog foreign key on "..." uses column "..."'>
    `ignore` only works on columns that are part of a **real** foreign key. If the relationship is declared in your schema file, remove it from `references` instead.
  </Accordion>

  <Accordion title="... is not part of any foreign key cycle">
    A `breakCycle` entry names a column that isn't in a cycle. Remove it, or fix the table or column name.
  </Accordion>

  <Accordion title='no such table "..." in the database'>
    `schema validate --source` found a table in the file that the database doesn't have, even if nothing is declared under it. Remove the entry, or fix its name. `plan` and `sync` ignore such empty entries, but validation reports them so the file stays clean.
  </Accordion>

  <Accordion title="unsupported file type">
    A schema file must end in `.yaml`, `.yml`, or `.json`.
  </Accordion>

  <Accordion title="schema file not found">
    The file passed to `--schema` doesn't exist. Paths are relative to the current directory.
  </Accordion>
</AccordionGroup>

## Cycles

<AccordionGroup>
  <Accordion title="unresolved cycle">
    ```text
    error: unresolved cycle: public.teams.lead_id is part of a foreign key cycle with no dependency break (add one, or turn off strictCycles for best-effort)
    ```

    You used `--strict-cycles` and the walk met a cycle with no `breakCycle` entry. Add the column named in the error, or another column in the same cycle, to `breakCycle`:

    ```yaml
    tables:
      teams:
        breakCycle: [lead_id]
    ```
  </Accordion>

  <Accordion title="... is NOT NULL but has to be loaded NULL and backfilled">
    A self-reference, broken cycle, or ignored foreign key column is `NOT NULL`. Tributary loads these columns as `NULL` first, so it can't load this table. Options:

    - Choose a different, nullable column in the cycle for `breakCycle`.
    - Remove the `ignore` on a `NOT NULL` column.
    - Make the column nullable on the source, if that's acceptable.
  </Accordion>
</AccordionGroup>

## Sync and target

<AccordionGroup>
  <Accordion title="refusing to write: target host is not in the target allowlist">
    The target's host isn't allowlisted. An empty allowlist blocks everything. Add the host:

    ```bash
    tributary config set allowlist 'localhost,dev-db.internal'
    ```

    Setting `allowlist` replaces the whole list, so include every host you need.
  </Accordion>

  <Accordion title="refusing to sync: source and target are the same database">
    The source and target point at the same database, perhaps through a pooler, or one is a replica of the other. Check both connection URLs.
  </Accordion>

  <Accordion title="target is missing N table(s) ... and schema creation is off">
    You passed `--no-create-schema` and some tables don't exist on the target. Run your migrations on the target first, or drop the flag.
  </Accordion>

  <Accordion title="target table ... is missing column ...">
    The target table exists but is missing a column the source has. Tributary never alters existing tables. Run your migrations so the target matches the source, or drop the target table so Tributary recreates it.
  </Accordion>

  <Accordion title="column ... is nullable in source but NOT NULL on target">
    Source rows may hold `NULL` there, which the target would reject. Align the target's column with the source.
  </Accordion>

  <Accordion title="column ... uses type ..., which doesn't exist on the target and isn't an enum">
    Tributary auto-creates enum types only. Create domains, composite types, and range types on the target first, for example by running your migrations.
  </Accordion>

  <Accordion title="foreign key violation loading ...">
    ```text
    error: foreign key violation loading public.orders (constraint orders_user_id_fkey): the referenced row isn't in this subset or on the target, likely a dangling reference in the source data
    ```

    Usually the source has a row that points at a row that doesn't exist. This can happen when the source constraint is `NOT VALID`, or the constraint exists on the target but not on the source. Find the dangling rows in the source, or add the column to `ignore` if the constraint is real on the source.
  </Accordion>

  <Accordion title="unique violation loading ...">
    A row on the target conflicts with an incoming row on a unique key **other than** the primary key. For example, a local user with the same email but a different ID. Delete or change the conflicting target row, then run the sync again. It resumes where it stopped.
  </Accordion>

  <Accordion title="A sync was interrupted">
    Run the exact same command again. Finished tables are skipped and shown as `already loaded (resumed)`. To start over instead, add `--fresh`. See [Resume](/reruns-and-resume#resume-after-an-interruption).
  </Accordion>

  <Accordion title="did not create foreign key ... the referenced table is outside this subset">
    This is a warning, not an error. A new target table references a table that isn't in the subset and doesn't exist on the target, so that one constraint was skipped. The data still loads.
  </Accordion>

  <Accordion title="Some foreign key columns are NULL on the target">
    That's expected for self-references, broken cycles, and ignored foreign keys whose referenced row is outside the subset. The **left null** column in the sync output counts them. Add the referenced rows as another seed if you need them.
  </Accordion>
</AccordionGroup>
