Tributary follows real foreign keys automatically. Many applications also have relationships the database doesn't enforce, such as Rails or Django associations, polymorphic columns, or composite references. You describe those in a **schema file**.

The schema file describes your _database_, not a single run. It holds no seeds and no connection strings, so you can commit it to your repository and share it with your team.

## When you need one

You need a schema file when:

- A column points at another table but has no `FOREIGN KEY` constraint, for example `orders.customer_ref`.
- A column points at different tables depending on a type column, for example `comments.subject_id` with `subject_type`.
- A real foreign key pulls in data you don't want, for example `audit_logs.actor_id`.
- Your schema has foreign key cycles and you want to choose where they break.

If none of these apply, you can skip the schema file. Tributary then follows database foreign keys only.

## Create a schema file

The fastest way to start is to generate one from your database:

```bash
tributary schema init --source prod
```

This writes `./schema.yaml` with:

- Every table in the source database.
- Each real foreign key as a **comment**, so you can see what's already followed.
- A **commented guess** for every `*_id` column without a foreign key, based on the column name.

```yaml schema.yaml (generated)
# Tributary schema file: the relationships your database doesn't declare.
# Real foreign keys are followed automatically and shown as comments.
# Review the guessed references and uncomment the right ones.
version: 1
defaultSchema: public
tables:
  orders:
    # user_id -> users.id  (database foreign key, followed already)
    references:
      # customer_id: customers.id   # guessed from the column name
  comments:
    references:
      # subject_id:   # no table matches "subject"; fill in "table.column"
```

Review the guesses and uncomment the right ones. Nothing guessed is active until you uncomment it.

| Option | Description |
| --- | --- |
| `-o, --output <file>` | Write somewhere other than `./schema.yaml`. |
| `--format json` | Write JSON. JSON can't hold comments, so it only lists the tables, without guesses. |
| `--force` | Overwrite an existing file. Without it, Tributary refuses. |

## File format

A schema file is YAML (`.yaml` or `.yml`) or JSON (`.json`). Both use the same structure.

```yaml schema.yaml
version: 1                  # required
defaultSchema: public       # optional; bare table names resolve here
tables:
  orders:
    references:
      customer_ref: users.id                                  # column -> table.column
  line_items:
    references:
      "tenant_id, order_id": [orders.tenant_id, orders.id]    # composite, paired in order
  comments:
    polymorphic:
      subject_id:
        typeColumn: subject_type
        targets: { Post: posts.id, Photo: media.photos.id }   # discriminator value -> table.column
  audit_logs:
    ignore: [actor_id]          # don't follow this real foreign key
  employees:
    breakCycle: [manager_id]    # cut a FK cycle: not followed, loaded NULL, backfilled
```

### Top-level fields

<ParamField path="version" type="1" required>
  The file format version. Must be `1`.
</ParamField>

<ParamField path="defaultSchema" default="public" type="string">
  The Postgres schema that bare table names resolve to. `schema init` picks `public` if it has tables, otherwise the schema with the most tables.
</ParamField>

<ParamField path="tables" type="object">
  One entry per table that needs configuration. Keys are `table` or `schema.table`, such as `"billing.invoices"`. Tables you don't list keep their default behavior.
</ParamField>

Each table entry can contain `references`, `polymorphic`, `ignore`, and `breakCycle`. Any other key is an error. Every section is optional, and a section with only comments under it is fine.

### Naming tables and columns

| Form | Example | Means |
| --- | --- | --- |
| `table` | `users` | `users` in `defaultSchema` |
| `schema.table` | `billing.invoices` | A table in another schema |
| `table.column` | `users.id` | A column in a `defaultSchema` table |
| `schema.table.column` | `media.photos.id` | A column in another schema |

## `references`

Declares a column that points at another table, like a foreign key the database doesn't have.

```yaml
tables:
  orders:
    references:
      customer_ref: users.id
      billing_account: billing.accounts.id
```

- The key is a column on this table.
- The value is the referenced `table.column`.

### Composite references

For a multi-column reference, list the columns separated by commas in the key, and the targets as a list in the same order:

```yaml
tables:
  line_items:
    references:
      "tenant_id, order_id": [orders.tenant_id, orders.id]
```

Rules:

- The number of columns must match the number of targets.
- All targets must be on the same table.
- A column can't reference itself.

## `polymorphic`

Declares a column whose target table depends on a **discriminator** column. This is the pattern Rails calls a polymorphic association.

```yaml
tables:
  comments:
    polymorphic:
      subject_id:
        typeColumn: subject_type
        targets:
          Post: posts.id
          Photo: media.photos.id
```

For a `comments` row with `subject_type = 'Post'` and `subject_id = 7`, Tributary follows the reference to `posts.id = 7`.

It works in both directions. When a `posts` row is in the subset and fans out to its children, Tributary finds comments with `subject_type = 'Post'` and a matching `subject_id`.

<ParamField path="typeColumn" type="string" required>
  The discriminator column, on the same table.
</ParamField>

<ParamField path="targets" type="object" required>
  A map from discriminator value to `table.column`. Needs at least one entry.
</ParamField>

If Tributary meets a discriminator value that isn't in `targets`, it skips that reference and prints a warning:

```text
warning: public.comments.subject_type: unrecognized polymorphic type value "Video", no matching target in the schema file; skipped
```

## `ignore`

Tells Tributary **not** to follow a real foreign key. Use it for references that would pull in unrelated data, such as audit actors or "last edited by" columns.

```yaml
tables:
  audit_logs:
    ignore: [actor_id]
```

- The column must be part of exactly one real foreign key on that table. Tributary reports an error otherwise.
- The constraint still exists on the target, so the column is loaded `NULL` first and backfilled afterwards where the referenced row happens to be in the subset. Otherwise it stays `NULL`.
- The column must therefore be nullable.

## `breakCycle`

Chooses where a foreign key cycle is cut. See [Cycles](/how-it-works#cycles) for the full explanation.

```yaml
tables:
  employees:
    breakCycle: [manager_id]
```

A `breakCycle` column:

- Is not followed during the walk.
- Is loaded `NULL`, then backfilled where the referenced row is in the subset.
- Must be part of a foreign key cycle. Tributary reports an error if it isn't.
- Must be nullable.

Without a `breakCycle` entry, Tributary breaks cycles automatically and tells you in the plan. Pass `--strict-cycles` to make an undeclared cycle an error.

## Which file is used

| Situation | File used |
| --- | --- |
| You pass `--schema <file>` | That file. It's an error if it doesn't exist. |
| You don't pass `--schema` | The first of `./schema.yaml`, `./schema.yml`, `./schema.json` that exists, in the current directory. |
| None of those exist | No schema file. Only database foreign keys are followed. |

Every run prints which file it used, for example `using schema ./schema.yaml`, or that it found none.

## Validate a schema file

```bash
# Check the format only
tributary schema validate

# Also check that every table and column exists in the database
tributary schema validate --source prod

# Check a specific file
tributary schema validate --schema config/tributary.yaml --source prod
```

Tributary reports every problem at once, with its location in the file:

```text
error: ./schema.yaml: invalid schema file:
  - tables.line_items.references."tenant_id, order_id": 2 columns but 1 target column
  - tables.comments.polymorphic.subject_id.targets: needs at least one discriminator value -> "table.column"
```

`schema validate` exits with a non-zero code on any problem, so you can run it in CI:

```yaml .github/workflows/schema.yml
- run: npx @bhuneshvar-k/tributary schema validate
```

<Tip>
  Without `--source`, validation only checks the file's structure. Add `--source` to catch typos in table and column names, and `breakCycle` entries that aren't part of a cycle.
</Tip>

## Good to know

- Declared `references` and `polymorphic` entries change which rows are collected. They don't change the load order, because the target only enforces real foreign keys.
- `plan` and `sync` re-read the schema file on every run. Editing it changes the run ID, so a changed file starts a new run instead of resuming an old one. See [Re-runs and resume](/reruns-and-resume#resume-after-an-interruption).
